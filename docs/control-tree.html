Understanding the Docking Control Tree

A docking layout consists of a host surface and a tree of layout elements. The tree can contain five element types. Visual elements such as splitters, tabs, title bars and docking guides are created at runtime and are not included in a saved layout.

Where a docking tree can be hosted

There are three hosting contexts. You add a DockSite directly to your XAML. The library creates a separate window when content floats. Auto-hidden content appears in a flyout inside the DockSite; the flyout is not a separate window.

Host 1 · DockSite

Add DockSite wherever the docking area should appear in your XAML. It obtains the owning AppWindow through XamlRoot.ContentIslandEnvironment. This allows it to close all floating windows before the application window closes.

Host 2 · floating window

When content is undocked, the library creates a FloatingWindowHost. This class wraps a standard Window; it does not inherit from Window. The window contains a FloatingWindowRoot with its own docking guides, so other content can be docked inside it.

Host 3 · auto-hide flyout

AutoHideFlyout contains a private grid that displays one ToolWindow at a time. Auto-hide is available only in DockSite. Floating windows do not have auto-hide strips or a flyout.

Elements allowed in a layout

Each layout slot contains one element. That element must be a SplitContainer, ToolWindowContainer, DocumentContainer, DocumentHost or Workspace; the serializer throws NotSupportedException for any other type. A SplitContainer can contain any number of valid layout elements. A DocumentHost can contain a nested layout made only of document containers and splits.

The library does not use DockingManager, TabView or Popup. Its tabs, title bars and auto-hide flyout are custom controls.

How SplitContainer stores panes and splitters

SplitContainer derives directly from Panel. Its Children collection contains both panes and generated splitters: all N panes come first, followed by N−1 DockSplitter elements. During layout, the splitters are positioned between the panes. Use GetPanes() when you need the panes; iterating over Children also returns the splitters.

How containers preserve their windows when templates change

Each DockingWindowContainer creates and owns a private Grid named windowsHost. The container assigns this grid to PART_ContentHost.Content. All hosted windows remain in the grid; selecting a tab changes their Visibility. Because the grid belongs to the container rather than the template, it survives when the template is reapplied.

Runtime state and the serializable layout model

The control tree is supported by two non-visual data layers. The internal runtime layer tracks objects that do not belong in the visual tree, such as collapsed auto-hide windows and floating-window hosts. The serialization layer represents the layout without UI controls. This separate model is used to save and load XML and allows the serialization logic to be unit-tested independently of WinUI.

Loading updates the existing layout instead of replacing the entire control tree. The loader reuses Workspace, DocumentHost, SplitContainer and container instances when their position or ID matches. If the saved layout has not changed, the existing controls remain in place.

Rules enforced by the layout system

  • Window type determines container type. A DocumentWindow is always placed in a DocumentContainer. Every other docking window is placed in a ToolWindowContainer.
  • Empty layout elements are removed. When a container becomes empty, it is removed from its parent. When a split has only one pane left, the split is replaced by that pane, which inherits the split's RelativeSize.
  • Splits with the same orientation are merged. Docking along the same axis adds the pane to the existing split at the appropriate end. Docking along the other axis creates a nested split.
  • Use the layout tree to determine location. Do not inspect the visual tree for this purpose. Immediately after a move, an element may not have a visual parent until WinUI completes the next layout pass.
  • Handle Relocated instead of Loaded. After a move and the following layout pass, the library raises Relocated at low dispatcher priority for every IRelocatable element in the moved subtree.
